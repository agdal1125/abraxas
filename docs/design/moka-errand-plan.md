# 모카의 빵 심부름 계획 — ER1

2026-11-02 · T014 계획·디자인 산출물 · 사람 검토 전 · 제품 코드·측정 데이터·에셋 변경 없음

**목표:** 모카를 만나 빵을 집고, 공방에 전한 뒤 빵집 진열대를 정리하고 돌아오는 한 에피소드를 만든다. 여섯 선택은 기존 의미와 순서를 지키며, 끊겼다가 돌아와도 바뀌지 않는다.

**구조:** 기존 Three.js 마을과 HTML 대화창을 유지한다. 모카 전용 단계 상태와 작은 진열 작업판만 추가한다. 서버가 선택·진행·완료의 원본을 가지며, 클라이언트는 서버가 확인한 상태를 화면에 옮긴다.

**담당:** 계획·디자인은 Codex `gpt-6-astra` / reasoning `high`. 후속 구현·아트는 agy Argon4(`gemini-4-argon-medium`), 현재 T014에 기록된 사용량 한도에서는 Codex `gpt-6.1-terra`로 대체한다. 새 구현 작업마다 Argon4 복귀 가능 여부를 먼저 확인한다. 검수·착수·병합·공유 기록은 Claude가 관리한다. 이 문서는 구현 착수나 배포 승인이 아니다.

### 확정 사항과 설계자의 추천안

이미 정해진 것은 거리 밖 대상 탭 시 자동 이동, Space·Enter·E, 숨김 이동 패드, 가로 화면과 회전 시 상태 유지, 30~60초 퍼즐·힌트·자동 완성이다. 이 항목은 다시 질문하지 않는다. 기존 문항 수·의미·가중치·순서·호감도 정책도 그대로다.

추천하는 구성은 **기존 공방 구역을 재사용하고, 진열은 빵집 앞에서 하는 한 구간**이다. 공방 안에 빵 진열 퍼즐까지 두면 `moka_03`의 빵집 맥락이 달라진다. 새 실내 씬을 만들면 동선·로딩·아트가 커진다. 범용 퀘스트 엔진·물리 운반·복잡한 가방·시간제한·오프라인 진행·다른 주민의 심부름은 추가하지 않는다.

## 2. 플레이어 경험 흐름

### 화면과 입력의 공통 원칙

상단에 **지금 할 일 한 줄**, 그 아래 작은 **들고 있는 물건 표시**를 둔다. 월드에서는 주인공 앞쪽에 작은 바구니가 함께 보인다. 빈손이면 ‘빈손’으로 표시한다. 목표 문구는 화면 폭에 맞게 줄바꿈하며, 정보를 자르지 않는다. 현재 목표 하나만 강조하고 측정 선택지 사이에는 강조 차이를 두지 않는다.

화면 구성 예:

```text
┌ 지금 할 일: 빵을 공방에 전하기 ───────┐
│ 들고 있는 물건: 호두빵 바구니          │
│                                      │
│       주인공과 바구니     받침대       │
│                                      │
│ 이동 조작 때만 패드 표시              │
└ 대화할 때는 아래에 대사와 선택지 ────┘
```

- 가까운 목표를 탭하면 바로 그 동작을 한다. 먼 목표를 탭하면 자동으로 걸어가며, 도착 시 거리·가림·현재 단계를 다시 검사한다. 화면 밖 목표는 한 줄 안내를 따라 직접 걸어서 찾는다. 미니맵이나 새 상시 실행 버튼은 만들지 않는다.
- 키보드는 이동키와 가까운 대상에 대한 Space·Enter·E를 유지한다. 대사·퍼즐에서는 DOM 버튼으로 초점을 옮긴다. 손으로 이동하면 자동 이동은 취소되지만 확정한 선택은 바뀌지 않는다.
- 선택 화면·퍼즐·저장 대기·세로 회전 안내 중에는 이동 입력과 자동 이동을 해제한다. 닫기나 확인에 쓴 탭이 뒤의 물건까지 실행하지 않게 현재 `token` 방식을 유지한다.
- 목표 소품은 고유한 모양과 이름으로 구별하고 48×48 이상 터치 영역을 확보한다. 글자 확대·본문 대비 4.5:1·키보드 포커스를 지킨다. 색만 보고 맞추게 하지 않는다.
- 저장 중에는 ‘선택을 저장하고 있어요.’, 연결 실패에는 ‘연결되면 이어갈 수 있어요.’와 ‘다시 연결’을 보여준다. 다시 연결은 같은 요청을 재전송한다. 다른 답을 고르는 버튼은 없다.

예약 손님·진열·시식·반죽은 빵집 앞 같은 작은 작업 구역에 묶는다. ‘공방에 전하기 → 진열대 정리 → 모카에게 돌아오기’ 사이에 다른 지역 심부름을 끼우지 않는다. 모카는 잠깐 주문대에 함께하거나 말을 건네어 원문의 질문 주체를 유지한다. 마지막 복귀는 멀리 다시 걷게 하기보다 진열대에서 모카가 있는 자리까지의 짧은 이동이다. 에피소드 전체 약 4.5분은 목표이며, 실측 전 보장이 아니다.

### 길과 물건 처리

`moka_01`의 a는 따뜻할 때 전하려는 지름길, b는 빵을 보호하려는 완만한 길이다. 선택 전에 두 의도를 원문으로 제시한다. 저장된 선택으로 자동 이동 경유점을 정하며, 실제로 밟은 길·속도로 답을 추정하지 않는다. 직접 다른 길로 돌아가거나 자동 이동을 중단해도 같은 답을 유지하고 전달은 가능하다.

가파른 길과 완만한 길은 짧은 두 동선으로 구별한다. 이동 조작 횟수·길 찾기 부담이 크게 벌어지지 않게 배치하며, 어느 길에도 장애물 시험·낙하·시간 보상·추가 호감도를 두지 않는다. 현행 월드 이동은 x/z 평면이므로 실제 높이 이동이 이미 있다고 가정하지 않는다. 언덕길 표현은 작은 배경 단차·길 굴곡·연출로 시작하고, 원문 상황이 납득되는지는 아트 검수에서 확인한다. 이를 위해 지형 전체나 충돌 엔진을 다시 만들지 않는다.

한 번에 운반하는 것은 호두빵 바구니 하나다. 버리기·자유 좌표 드롭은 없다. 배달 중 잠깐 놓고 싶다면 두 길이 합류하는 고정 받침대 `moka-rest`만 사용한다. 그곳에 놓아도 다음 목표는 바구니 다시 집기이며, 전달로 처리하지 않는다. 엉뚱한 물건을 누르면 ‘이곳에 전할 빵은 아니에요.’라고 안내하고 바구니를 유지한다. 장부·시식 빵·반죽 틀·쿠키는 해당 자리에서의 짧은 동작용이며 별도 가방 슬롯에 저장하지 않는다.

### 30~60초 진열 퍼즐

빵 세 모양이 두 개씩, 총 여섯 개다. 각 자리에는 빵과 같은 **모양 표식과 이름**이 있다. 빵을 하나 고르고 같은 모양의 빈 자리를 고르면 놓인다. 같은 모양 두 조각 사이에 숨은 순서는 없다. 잘못 놓으면 ‘표식을 한 번 더 살펴볼까요?’라고 알리고 원래 선택 상태로 돌아간다. 실패 횟수나 감점은 없다.

1단은 세 쌍을 한 줄로, 3단은 세 쌍을 세 높이로 보여준다. 모바일 작업판에서는 어느 배치든 동일 크기의 여섯 자리를 제공한다. 색·조각 수·필요 탭 수·힌트 접근성을 같게 한다. 3단에만 균형 잡기나 무너짐을 추가하지 않는다. 높이 쌓는 위험은 선택 전 원문의 상황이고, 숙련도를 재는 벌칙은 아니다.

- ‘힌트’: 아직 놓지 않은 빵 하나와 가능한 자리를 함께 표시한다. 횟수 제한이 없고 측정 선택에 관한 힌트는 주지 않는다.
- ‘자동으로 정리하기’: 서버가 남은 자리의 올바른 배치를 만들고 수동 완료와 같은 단계로 전환한다. 처음부터 사용할 수 있고 별도 경고나 불이익이 없다.
- ‘잠깐 닫기’: 이미 확인된 배치는 유지한다. 다시 진열대를 누르면 같은 배치로 열린다. 다음 측정 문항은 퍼즐 완료 확인 후에만 열린다.
- 30~60초는 관찰·탭·읽기 시간을 포함한 목표다. 카운트다운·강제 종료·최소 소요 시간은 없다. 오래 걸리면 플레이 시간을 늘리도록 두고 자동 완성을 계속 제공한다.

## 3. 기존 측정 문항 연결

아래 a/b 문구는 `content/scoring/items.json`의 원문이다. 여섯 ID를 각 한 번, `01 → 02 → 03 → 04 → 05 → 06` 순서로 묻는다. 표의 축·가중치는 **개발자 검수용**이며 화면에는 표시하지 않는다. 상황 속 기존 임시 인물 표기만 화면용 이름 ‘모카’로 바꾸고 의미를 추가하거나 생략하지 않는다.

| 문항 / 기존 종류 | 붙일 지점 | a 원문 | b 원문 | 보존할 측정 연결 |
| --- | --- | --- | --- | --- |
| `moka_01` / `errand` | 모카의 배달 부탁 직후, 바구니를 집기 전 | 빵이 가장 따뜻할 때 전하려고 가파른 지름길로 달려간다 | 빵이 눌려 상하지 않도록 완만한 길로 안전하게 걸어간다 | D: a +12 / b −12. 선택이 경로 연출을 정하며 도착 속도는 무관 |
| `moka_02` / `dialogue` | 배달 후 빵집에 돌아와 예약 장부와 손님의 말이 다른 장면 | 장부에 적힌 예약 내역을 함께 보며 사실부터 확인한다 | 손님이 민망하지 않게 먼저 안심시키며 원하는 빵을 준다 | B: a −12 / b +12. 사실 확인과 마음 배려의 차이를 보존 |
| `moka_03` / `puzzle_pre` | 빵집 진열대를 정리하기 직전 | 빵이 떨어져 상하지 않게 안정적인 1단 진열을 택한다 | 가게 밖에서도 한눈에 띄는 높은 3단 진열을 노린다 | D: a −12 / b +12. 퍼즐 배치 방식 선택을 먼저 저장 |
| `moka_04` / `puzzle_post` | 진열 완료 후 남은 시식용 조각 빵을 나누기 직전 | 아까부터 지친 기색으로 서성이던 이웃에게 먼저 건넨다 | 누구에게나 공평하게 같은 크기로 잘라 접시에 담아 둔다 | B: a +12 / b −12. 지친 이웃은 미리 장면에 보이되 답을 추천하는 연출 금지 |
| `moka_05` / `dilemma` | 모카가 저녁 축제 특별 파이 수량을 묻는 준비대 | 손님이 몰릴 기회를 살려 평소보다 두 배 많이 굽자 | 남아 버리는 손실이 없게 예약된 수량만큼만 구워 내자 | D: a +12 / b −12. 가치 태그 a 성취·자극, b 안전·전통 유지 |
| `moka_06` / `dialogue` | 모카에게 돌아와 기울어진 꽃모양 쿠키를 본 뒤 | 오븐 열기가 쏠린 듯하다며 기울어진 원인을 짚어 준다 | 정성껏 구운 마음이 예쁘다며 고소한 향기부터 칭찬한다 | B: a −12 / b +12. 몸짓으로 답을 추정하지 않고 원문 의도를 선택 |

모든 문항의 `segment=ep_moka`, `npc=moka`, `kind`, `axis`, `picks`, `w`, `values`를 유지한다. 새 측정 문항·보조 가중치를 만들지 않는다. 모카의 담당 축별 세 문항, 전체 38문항·별도 타이브레이커 4개, NPC 기대 답변이 없는 14문항을 보존한다.

**퍼즐 성공·실패·속도·시도 횟수·힌트·자동 완성·운반 경로·걸음 속도는 성향 점수와 가치 태그에 영향을 주지 않는다.** 자동 완성도 수동 정리와 같은 심부름 완료 조건이다. 힌트를 쓰면 호감도 보상이 줄어드는 등의 간접 차이도 두지 않는다.

측정 반응은 서버가 원래 NPC 누적 상태에서 판정한 공감/생각 두 종류만 사용한다. 선택 전 선호 암시, 선택 직후 하트·물음표 버블은 금지한다. 보상은 기존 정책의 담당 심부름 완료 +8을 모카에게 회차당 한 번만 적용하고, 에피소드 종료 때만 하트 5칸으로 보여준다. 문항별 기대 일치 보상과 완료 보상을 구별하며, 반죽 수량·퍼즐 점수로 추가 보상하지 않는다.

## 4. 데이터·상태 모델

### 필요한 최소 데이터

새 `content/quests/moka-errand.json`은 단계별 대상 ID, 선택 문항 ID, a/b의 동작 연결, 두 길의 경유점 ID, 빵 여섯 조각과 허용 자리만 담는다. 가중치·NPC 기대 답변·보상 수치를 복사하지 않는다. 서버는 빌드에 포함된 이 파일과 측정 데이터를 읽는다. 클라이언트가 보낸 콘텐츠나 다음 단계 표는 사용하지 않는다.

진행 상태는 `playId`, `contentVersion`, `revision`, 현재 구간, 확정 답변 목록, 완료 에피소드, 모카 단계·바구니 위치·확정 진열 배치를 포함한다. 회차 ID와 콘텐츠 버전은 서버가 정한다. 콘텐츠 버전은 측정 JSON 세 파일·심부름 계약·질문 의미를 담는 양 언어 번역과 ink의 내용 해시를 묶어 고정한다. 클라이언트도 빌드에 같은 해시를 포함하고, N/U는 스냅샷과 일치하는지 확인한 뒤 문항을 연다. 캐시된 옛 번들과 다르면 ‘새 버전을 불러온 뒤 이어갈 수 있어요.’로 안내하고 진행을 보류한다. 이전 버전을 지원하지 못하는 서버도 조용히 다른 질문을 보여주지 않고 재개를 보류한다.

```ts
type MokaPhase =
  | "locked" | "choose_route" | "pick_up" | "deliver"
  | "reservation" | "reservation_action" | "choose_display" | "arrange"
  | "share" | "share_action" | "order" | "order_action"
  | "return" | "feedback" | "report" | "completed";

type BasketLocation = "source" | "player" | "moka-rest" | "delivered";
type BreadId = "walnut-1" | "walnut-2" | "roll-1" | "roll-2" | "flower-1" | "flower-2";
type SlotId = "walnut-left" | "walnut-right" | "roll-left" | "roll-right" | "flower-left" | "flower-right";
type MokaState = {
  phase: MokaPhase;
  basket: BasketLocation;
  placements: Partial<Record<SlotId, BreadId>>;
  completedAt: string | null;
};
type Choice = { id: string; pick: "a" | "b" };
type PendingCommand = { key: string; expectedRevision: number; command: Command };
type LocalSync =
  | { status: "ready" }
  | { status: "saving" | "retry"; pending: PendingCommand };
```

`Command`은 §5의 요청 종류다. `Choice`는 이번에 지원하는 실제 a/b 문항 집합에 대한 스케치이며 범용 선택지 형식을 바꾸지 않는다. 들고 있는 물건은 `basket === "player"`일 때만 바구니로 계산한다. 서버가 받은 `carriedItem` 값을 그대로 저장하는 필드는 없다. `route`와 `display`도 각각 확정 `moka_01`, `moka_03` 답에서 얻고 별도 수정 가능한 사본을 두지 않는다.

화면용 `mokaView(snapshot): MokaView`는 `phase`, `basket`, `placements`, `objectiveKey`, `activeTargetIds`, `resumePointId`와 파생 `route: "shortcut" | "gentle" | null`, `display: "low" | "high" | null`을 반환한다. U와 W가 같은 값을 사용한다. W의 공개 계약은 `Village.setMokaView(view: MokaView)`다. 답변 없는 `MokaState`만 받아 분기를 추측하지 않으며, `MokaView`를 별도로 서버에 저장하지 않는다.

### 전이와 서버 조건

| 현재 단계 | 허용 입력 | 다음 단계 / 상태 변경 |
| --- | --- | --- |
| `locked` | 허브에서 `open_episode(moka)`, 아직 끝내지 않은 에피소드 | `choose_route`, 바구니 `source` |
| `choose_route` | `choice(moka_01, a 또는 b)` | `pick_up` |
| `pick_up` | `pickup(moka-basket-source)`, 바구니가 `source` | `deliver`, 바구니 `player` |
| `deliver` | `set_down(moka-rest)` / `pickup(moka-rest)` | 단계 유지, `player ↔ moka-rest`만 전환 |
| `deliver` | `deliver(moka-workshop-dropoff)`, 바구니가 `player` | `reservation`, 바구니 `delivered` |
| `reservation` | `choice(moka_02, a 또는 b)` | `reservation_action` |
| `reservation_action` | `act`, 02 선택에 맞는 장부 또는 빵 전달 대상 | `choose_display` |
| `choose_display` | `choice(moka_03, a 또는 b)` | `arrange`, 배치는 처음에 빈 상태 |
| `arrange` | `place(breadId, slotId)`, 남은 빵과 맞는 빈 자리 | 배치만 저장. 여섯 자리 충족 시 `share` |
| `arrange` | `auto_arrange` | 서버가 남은 배치를 채운 뒤 `share` |
| `share` | `choice(moka_04, a 또는 b)` | `share_action` |
| `share_action` | `act`, 04 선택에 맞는 이웃 또는 공용 접시 | `order` |
| `order` | `choice(moka_05, a 또는 b)` | `order_action` |
| `order_action` | `act`, 05 선택에 맞는 반죽 준비 묶음 | `return` |
| `return` | `talk(B)` | `feedback` |
| `feedback` | `choice(moka_06, a 또는 b)` | `report` |
| `report` | `complete(B)`, 배달·진열·후속 동작·여섯 답변 충족 | `completed`와 완료 시각·한 번의 보상 사건을 한 트랜잭션에서 저장 |
| `completed` | 다시 누르기·재전송 | 기존 완료 상태 반환. 답변·보상·완료 횟수는 증가하지 않음 |

`act`의 대상은 콘텐츠에 정한 `moka-ledger` / `moka-reservation-bread`, `moka-tired-neighbor` / `moka-tasting-plate`, `moka-dough-double` / `moka-dough-reserved` 중 현재 답에 맞는 하나다. 각 쌍은 저장된 선택의 결과를 실행하는 대상이며 다시 고르는 선택지가 아니다. 완료 후 구간 이동도 서버가 완료 에피소드 수로 계산한다.

### 선택 확정·재시작·이어하기

1. 선택 탭 직후 같은 화면의 추가 입력을 잠근다. `{playId, itemId, pick, key}`를 로컬 대기 기록에 먼저 남긴 뒤 서버에 요청한다. 로컬 저장에 실패하면 전송·반응을 시작하지 않고 저장 문제 안내를 보여준다. 화면을 열어 둔 동안 선택은 잠근 채 유지한다.
2. 서버 확인 뒤 확정 답과 새 `revision`을 로컬에 기록하고 반응을 보여준다. 확인 후 로컬 기록 실패 시에도 서버 답을 취소하지 않는다. 입력을 잠그고 재조회하여 복구한다.
3. 새로고침·브라우저 뒤로 가기·앱 복귀 시 Firebase의 같은 익명 사용자로 서버 현재 회차를 먼저 읽는다. 대기 기록은 같은 키·같은 본문으로 재전송한다. 응답이 유실됐어도 새 답을 묻지 않는다.
4. 선택 확정 뒤 동작 중 종료했다면 `reservation_action` 같은 미완료 동작부터 이어간다. 퍼즐은 서버가 확인한 배치부터, 전달 직후 종료는 빈손과 공방 바구니부터 복구한다. 미확정 화면 연출만 되풀이될 수 있고 측정·보상은 되풀이되지 않는다.
5. 위치 좌표·걸음 경로는 서버에 저장하지 않는다. 재개 시 해당 단계의 검증된 안전 지점에서 시작하고, 물건 위치는 서버 상태로 복구한다. 진행 중 세로 회전은 현재 위치와 대사·작업판 상태를 유지한다. 새로고침 때의 안전 지점 복귀와 구별한다.
6. 다중 탭에서 다른 답을 먼저 저장했다면 서버 최초 답이 원본이다. 늦은 탭은 충돌을 받고 새 상태를 읽는다. ‘다른 화면에서 이어진 내용을 불러왔어요.’로 안내하고 기존 답을 다시 묻지 않는다.
7. 진행 중 ‘처음부터’는 회차를 지우거나 새 `playId`를 만드는 기능으로 제공하지 않는다. 같은 사용자의 활성 회차를 다시 불러온다. 새 회차·초대권 소모는 서버의 회차 개설 권한으로만 허용한다. 재플레이 API가 없는 ER1에서 임의 무료 재시작을 구현하지 않는다.

완전 오프라인 진행은 제외한다. 연결이 끊기면 마지막 확정 상태에서 대기하며 같은 명령만 재전송한다. 한 번도 서버에 도달하지 않은 선택을 로컬 저장까지 고의로 지워 번복하는 것은 서버가 관찰할 수 없다. 서버가 수신해 확정한 답의 불변성과, 정상적인 새로고침·재접속 복구를 보장 범위로 삼는다. 기기 저장소 삭제로 익명 인증 자체가 사라진 경우의 복구도 보장하지 않는다.

기존 `abraxas-prototype`은 인증 없는 로컬 자료다. 공식 서버 기록으로 자동 승격하면 클라이언트 값을 믿게 된다. **추천:** 원본을 그대로 보존하고 기존 회차는 로컬 체험으로 이어가며, 새 서버 회차와 별도 저장 키로 분리한다. 기존 답을 공식 답으로 가져오거나 같은 기존 회차에서 다시 묻지 않는다. 이 전환의 사용자 경험은 마지막 질문에서 확인한다.

ink도 같은 확정 순서를 지킨다. 현행 `ChooseChoiceIndex()` 선호출을 그대로 쓰지 않고, 태그 검증 → 로컬 대기 기록 → 서버 확정 → ink 선택 적용·반응 순서로 연결한다. 재개는 서버 단계에 맞는 knot로 진입하며 이미 확정된 선택을 다시 화면에 띄우지 않는다. ink 오류나 누락 시에도 같은 원문 문항만 표시하고 일반 문항 경로와 이중 제출하지 않는다.

## 5. 서버 저장 설계

### 신뢰 경계와 현실적인 보장

서버는 인증된 사용자의 회차, 다음 문항, 선택의 불변성, 바구니의 보관 위치, 허용된 진열 배치, 순서와 완료 보상을 직접 판정한다. 요청의 점수·호감도·완료 여부·다음 단계·사용자 ID·콘텐츠 버전은 신뢰하지 않고 받지 않는다.

클라이언트는 ‘이 대상에 이 동작을 하고 싶다’는 명령만 보낸다. 이것도 서버 상태·허용 목록으로 검증한다. **실제 화면에서 공방까지 걸었다는 사실까지 증명하는 설계는 아니다.** 좌표나 경과 시간을 추가로 보내도 신뢰 경계가 해결되지 않는다. 서버 이동 시뮬레이션은 ER1에 넣지 않으며, 순서가 맞는 API 호출 자동화를 완전히 막는다고 보고하지 않는다. 인증·App Check·속도 제한은 별도로 적용한다.

Firebase ID 토큰 검증 후 그 토큰의 uid만 사용한다. App Check 토큰도 같은 프로젝트의 것으로 검증한다. Firebase 공식 문서의 [ID 토큰 검증](https://firebase.google.com/docs/auth/admin/verify-id-tokens)과 [사용자 정의 백엔드 App Check 검증](https://firebase.google.com/docs/app-check/custom-resource-backend)을 구현 근거로 삼는다. 토큰 원문은 이 문서나 로그에 남기지 않는다.

### 엔드포인트와 요청

아래는 모두 **신규 제안**이다. 표준 `net/http`의 메서드·경로 라우팅과 기존 `AuthMiddleware`, `UIDFromContext`, `DecodeJSON`, `WriteJSON`, `WriteError`를 사용한다.

| 메서드·경로 | 요청 | 응답·조건 |
| --- | --- | --- |
| `POST /v1/plays` | 빈 객체 `{}`, `Idempotency-Key` | `201` 새 회차 또는 `200` 기존 활성 회차. 서버 발급 `playId`, 프롤로그 상태. uid별 최초 서버 회차만 무료 개설, 이후 회차는 서버의 재플레이 권한 없으면 `409 replay_not_ready` |
| `GET /v1/plays/current` | 본문 없음 | `200` 현재 회차 스냅샷. 없으면 `404 play_not_found`. 로컬 ID를 잃어도 같은 uid로 재개 |
| `GET /v1/plays/{playId}` | 본문 없음 | `200` 소유 회차 스냅샷. 타인 회차·없는 회차는 동일한 `404` |
| `POST /v1/plays/{playId}/commands` | `expectedRevision`, `command`, `Idempotency-Key` | `200` 명령 영수증과 결과 스냅샷. 선택·행동·완료 모두 한 경로로 처리 |

토큰은 `Authorization: Bearer …`, App Check는 `X-Firebase-AppCheck` 헤더로 전달한다. 변경 요청의 멱등성 키는 클라이언트가 생성한 UUID이며 대기 기록과 함께 저장한다. 생성 API의 키 범위는 uid, 명령 API의 키 범위는 uid·playId다. `playId`는 서버가 암호학적 난수로 발급한다. 현재 클라이언트 `newId()`의 시간·난수 대체 방식은 서버 회차 발급에 쓰지 않는다.

```json
{
  "expectedRevision": 7,
  "command": { "kind": "choice", "itemId": "moka_01", "pick": "a" }
}
```

```json
{
  "expectedRevision": 9,
  "command": { "kind": "deliver", "targetId": "moka-workshop-dropoff" }
}
```

`command`의 종류별 필드는 아래처럼 한정한다. 예시 revision은 설명용이며 실제 서버 값으로 보낸다.

| `kind` | 필수 필드 | 서버가 정하는 것 |
| --- | --- | --- |
| `open_episode` | `npcId` | 허브·완료 목록 검사, 현재 에피소드 설정 |
| `choice` | `itemId`, `pick` | 허용 문항·순서·가중치·NPC 반응·다음 단계 |
| `pickup`, `set_down`, `deliver`, `act`, `talk`, `complete` | `targetId` | 현재 단계와 확정 답에 맞는 대상인지 검사 |
| `place` | `breadId`, `slotId` | 중복 없는 빵·빈 자리·모양 일치 검사 |
| `auto_arrange` | 추가 필드 없음 | 남은 배치와 퍼즐 완료 |
| `finish_segment` | 추가 필드 없음 | 다른 기존 구간의 필수 답 충족 후 서버가 다음 구간 계산. 모카에서는 사용 금지 |

모카 직전의 구간도 인증된 서버 진행이어야 한다. 따라서 최소한 **기존 모든 문항의 확정·기존 구간 전환**은 함께 서버로 옮긴다. 프롤로그 3 → 허브 → 선택한 미완료 에피소드 → 완료 횟수별 막간 → 다음 허브의 현행 흐름을 검증한다. 다른 주민의 새로운 행동 퀘스트는 만들지 않으며, 기존 대화만으로 그 주민의 심부름 보상을 새로 지급하지 않는다. 축제·문은 기존 필수 문항 순서를 검증하되 새 고백·결과 카드·초대권 기능은 후속 단계다. 테스트 전용 모카 진입 fixture는 테스트 코드 안에서만 사용하고 운영 API에 시작 구간 우회 필드를 두지 않는다.

### 응답 스케치

```json
{
  "receipt": {
    "key": "<요청 UUID>",
    "appliedRevision": 10,
    "reaction": null
  },
  "snapshot": {
    "playId": "<서버 발급 ID>",
    "contentVersion": "<고정 콘텐츠 해시>",
    "revision": 10,
    "segment": "ep_moka",
    "completedEpisodes": [],
    "answers": [{ "id": "moka_01", "pick": "a" }],
    "moka": {
      "phase": "reservation",
      "basket": "delivered",
      "placements": {},
      "completedAt": null
    }
  }
}
```

예시는 모카 관련 답만 줄여 썼다. 실제 `answers`에는 해당 회차의 앞선 확정 답도 들어간다. NPC 문항 선택 응답의 `reaction`은 `empathy` 또는 `thinking`, NPC 없는 문항과 비측정 명령에서는 `null`이다. 기대 극·성향 수치·유형은 플레이 도중 응답에 넣지 않는다. 모카 완료 뒤에만 `snapshot.episodeEnd: { npcId: "moka", hearts: 0..5 }`를 제공하고 GET으로도 복구한다. 하트는 화면용 칸 수이며 실제 호감도 숫자는 노출하지 않는다. 채움은 서버 최종 호감도를 20으로 나눈 내림값만큼 다섯 칸을 채우는 표시안을 사용한다. 이는 새 보상이나 고백 성공 기준이 아니다. 화면에는 숫자를 쓰지 않는다.

GET은 동일한 스냅샷을 반환하며 `receipt`는 없다. 오류는 기존 형식 `{"error":"revision_conflict"}`처럼 짧은 코드로 유지하고 UI가 문구로 바꾼다. `400` 형식·필드 오류, `401` 인증 오류, `403` App Check 오류, `404` 회차 없음·비소유, `409` 상태·키·선택 충돌, `413` 본문 초과, `422` 허용하지 않는 배치·행동, `429` 요청 제한, `503` 저장 일시 실패를 구분한다. `409` 후에는 GET으로 재조회한다. 버전 미지원은 `409 content_version_unavailable`로 재개를 보류한다.

### 원자적 저장과 멱등성

권장 저장 구조는 `players/{uid}`의 활성 회차 포인터와 `players/{uid}/plays/{playId}`의 상태 문서, 그 아래 `commands/{key}` 영수증이다. 답변은 최대 42개의 작은 배열로 상태 문서에 두어 순서를 보존한다. 모카 완료는 `events/moka-errand-completed`라는 고정 사건 ID로 남긴다. 상태 문서와 필요한 영수증·완료 사건을 같은 Firestore 트랜잭션에 기록한다.

1. 인증·형식 검증 후 트랜잭션에서 회차 소유·버전·기존 영수증·상태를 읽는다. 키의 요청 지문은 종류·본문·경로·기대 revision을 정규화해 서버에서 계산한다.
2. 같은 키·같은 본문이면 기존 `receipt`를 반환한다. revision이 바뀌었다고 기존 성공을 실패로 바꾸지 않는다. 같은 키·다른 본문은 `409 idempotency_conflict`다. 스냅샷은 최신 상태일 수 있으며 클라이언트는 낮은 revision으로 되돌리지 않는다.
3. 새 키일 때는 먼저 의미상 중복을 검사한다. 같은 문항의 같은 답·이미 끝난 모카 완료는 기존 결과를 돌려주고 반응·보상·revision을 다시 늘리지 않는다. 같은 문항의 다른 답은 항상 `409 choice_locked`다. 그 외 새 동작은 `expectedRevision`과 현재 revision이 같아야 한다. 실패 요청과 새 키를 남발한 의미상 중복에는 새 영수증을 쌓지 않는다.
4. 허용되는 전이만 계산하고 답변·물건·배치·revision·영수증을 원자적으로 저장한다. 퍼즐은 같은 빵 중복, 점유된 자리, 다른 모양, 허용 목록 밖 ID를 거부한다. 자동 완성은 요청의 완성 배열을 받지 않고 서버에서 만든다.
5. 마지막 보고에서는 여섯 답, 바구니 `delivered`, 진열 완성, 02·04·05의 행동 완료, 모카 복귀를 확인한다. 완료 사건이 없을 때만 생성하고 완료 에피소드 수를 늘린다. 전이 함수는 서버 상태를 읽어 판단하며 `completed: true` 요청을 받지 않는다.
6. 완료 사건이 이미 있으면 새 키로 와도 중복 보상하지 않는다. 답과 완료 사건은 회차 결과의 근거이므로 임의로 지우지 않는다. 영수증 정리 정책이 생겨도 최초 답·고정 완료 사건을 통한 의미상 중복 방지는 유지한다.

Firestore 트랜잭션은 충돌 시 재실행될 수 있으므로 콜백 안에서 HTTP 응답·UI 반응·외부 호출을 실행하지 않는다. 성공 응답은 커밋 뒤에 보낸다. 이는 Firebase의 [트랜잭션 문서](https://firebase.google.com/docs/firestore/manage-data/transactions)를 따른다.

### 검증·보안·보상 데이터

- 모든 변경 요청은 64KB 이하의 단일 JSON 객체다. `DecodeJSON`의 알 수 없는 필드·뒤따르는 JSON 거부를 재사용하되, 종류별 command도 엄격하게 해석한다. `null`, 빠진 필드, 중복 JSON 키, 음수·소수 revision, 잘못된 UUID·긴 ID·경로 구분자·종류에 불필요한 필드를 거부한다. 공용 디코더를 강화하면 기존 호출자 테스트도 유지한다.
- 기존 10초 요청 context를 저장 호출까지 전달한다. 제한 시간·응답 유실 시 ‘미저장’으로 단정하지 않고 같은 키 재전송과 조회로 확인한다. 클라이언트도 응답을 런타임 검증한다. 누락되거나 모르는 단계는 실행하지 않는다.
- uid별·IP별 제한을 실제 여러 서버 인스턴스에 걸쳐 적용한다. ER1 제안 상한은 uid당 분당 변경 요청 60회·조회 120회, IP당 분당 전체 600회이며 사용자 테스트로 조정한다. 이는 측정 수치가 아니다. 공유 제한 카운터는 보안용 짧은 수명 자료로 따로 두고 raw IP를 영구 게임 기록에 넣지 않는다. 전달 헤더의 IP를 무조건 믿지 않고 배포 프록시의 신뢰 범위를 확인한다. 메모리 한 인스턴스 제한만으로 운영 보장을 주장하지 않는다.
- 이름·자유 입력·좌표·소요 시간·힌트 횟수는 저장하지 않는다. 심부름 단계·바구니 위치·배치는 선택 로그를 이어가기 위한 최소 진행 자료다. 저장 실패 로그에 요청 본문·토큰·사용자 이름을 넣지 않는다. 현재 요청 로그의 실제 URL path에는 새 사용자 회차 ID가 들어갈 수 있으므로 `/v1/plays/{playId}/commands` 같은 라우트 이름만 남기도록 수정한다.
- Go `Data.Score()`의 전체 답 검증은 유지한다. 기존 누적 루프를 `Progress` 같은 부분 계산 진입점과 공유하고, 서버가 검증한 현재 로그에 대한 NPC 상태·반응만 계산한다. 최종 결과는 전체 로그로 `Score()`를 다시 호출해야 한다. 부분 결과를 완성된 성격 결과로 저장하지 않는다.
- 기존 완료 +8을 코드 상수로 흩뿌리지 않는다. 후속 전용 패키지에서 `rules.json`에 `errandAffinityGain: 8`만 추가하고 SCHEMA·검증기·TS/Go 파서에 연결한다. **기존 수치나 문항 가중치 변경은 없다.** 완료 사건의 합산은 기존 답변 계산과 분리하고 기존 상한으로 clamp한다. 기존 골든 fixture는 그대로 통과해야 한다. 데이터 형식 확장·보상 연결은 Claude가 별도로 검수하며, 값을 다르게 바꾸려면 사람 승인이 필요하다.
- 현재 최종 결과·초대권 저장 API는 없다. ER1은 서버 확정 선택과 모카 완료까지를 인수 범위로 삼는다. 기존 클라이언트 결과 화면을 공식 저장 결과로 승격하지 않는다. 전체 서비스 공개와 유료·초대권 재플레이는 후속 저장 작업의 검증이 끝나기 전 완료로 표시하지 않는다.

### 사람 승인 필요인 환경 작업

**Firestore 규칙 변경·배포·비밀값 변경은 사람 승인 필요.** 개발·에뮬레이터 검증과 실제 운영 변경을 구별한다. 새 규칙 파일이 필요하다면 클라이언트 읽기·쓰기를 전부 거부하는 초안을 만들고, 승인 후 배포한다. 보안 규칙을 열어 클라이언트 직접 저장으로 우회하지 않는다.

서버 SDK의 접근은 Firestore 클라이언트 규칙이 아닌 IAM으로 통제되므로 서버에서 소유권 검사가 필요하다. [Firestore 보안 개요](https://firebase.google.com/docs/firestore/security/overview)를 따른다. Firebase Anonymous Auth·App Check 등록, Cloud Run 실행 계정과 최소 권한, 콘텐츠 파일 포함 빌드, Hosting의 API 연결·허용 origin·보안 헤더는 환경 패키지에서 확인할 항목이다. 실제 프로젝트 값을 이번 계획에서 추측하지 않는다. 비밀값은 Secret Manager와 git 제외 `.env.local`만 사용하며 서비스 계정 JSON을 배포 파일에 넣지 않는다.

새 의존성은 서버의 허용된 Firebase Admin SDK·Firestore 클라이언트와 클라이언트의 Firebase 인증·App Check SDK 정도로 한정한다. 추가 전 관리 상태·실제 버전·용량을 확인하고 ADR와 PR에 이유를 적는다. API 요청은 표준 `fetch`, Go HTTP는 표준 라이브러리를 쓴다. Firebase Web SDK로 Firestore를 직접 읽고 쓰는 기능은 넣지 않는다.

### 반드시 남길 검증 증거

- **측정:** 여섯 선택의 모든 a/b 조합에서 행동·힌트·속도를 바꿔도 같은 답 로그이면 같은 성향·가치가 나와야 한다. 수동·자동 진열 완료의 보상도 같다. 기존 38+4 골든과 순서 검사는 그대로 둔다.

- **복구:** 서버 커밋 후 응답 유실, 로컬 대기 기록 실패, 확인 뒤 로컬 쓰기 실패, 서버와 클라이언트 번들의 콘텐츠 버전 불일치, 인증 만료를 재현한다. 응답 유실에는 재전송이 같은 효과를 반복하지 않아야 하고, 버전 불일치에는 문항을 열지 않아야 한다. 재개한 길·진열 방식은 확정 답과 같아야 한다.
- **입력·월드:** 844×390, 740×360, 960×540, 1280×720에서 바구니·목표·작업판·선택지 겹침을 확인한다. 두 길·받침대·진열대·모카가 모두 도달 가능해야 한다. 숨김 조이스틱·Space/Enter/E·터치 취소·대화 닫기 입력이 회귀하지 않아야 한다.
- **실기기:** iOS Safari·Android·카카오톡 인앱에서 한 구간을 끝내고 회전·백그라운드·연결 끊김을 확인한다. 30~60초 퍼즐과 약 4.5분 에피소드는 실제 시간을 기록하고, 초과하면 측정 문구를 줄이기보다 불필요한 이동·비측정 연출을 먼저 줄인다.
- **명령:** 클라이언트 `npm run typecheck`, `npm test`, `npm run ink`, `npm run build`, `npm run check:size`; 루트 `npm run check:scoring`; 서버 `gofmt -l .`, `go vet ./...`, `go test ./...`, `govulncheck ./...`. 의미 있는 서버 동시성 테스트에는 `go test -race ./...`도 실행 가능한 환경에서 사용한다. 명령은 각 디렉터리에서 별도로 실행한다.
