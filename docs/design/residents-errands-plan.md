# 다른 주민의 생활 문제 계획 — RS1

2026-11-02 · 로드맵 3단계 · 사람 검토용 제안 · 제품 코드·측정 데이터·에셋 수정 없음

**목표:** 루미의 축제 준비, 에코의 책 정리, 오르의 종과 등불 수리를 실제로 걷고 옮기고 맞추는 생활 문제로 만든다. 주민마다 기존 여섯 문항을 같은 뜻과 순서로 묻고, 행동을 끝낸 뒤에만 심부름을 완료한다.

**추천 구조:** 주민별 상태 전이와 콘텐츠 계약을 만든다. 모카의 통신·저장·중복 방지·완료 보상 처리를 공유하되, 모든 주민을 해석하는 범용 심부름 엔진은 만들지 않는다. 한 주민을 끝까지 연결하고 검증한 다음 다음 주민으로 넓힌다.

**기술·담당:** 현행 Three.js + TypeScript + HTML UI, ink, Go API를 유지한다. 계획·디자인은 Astra High, 구현·아트는 agy Argon4, 사용량 한도일 때만 Terra로 대체한다. Claude가 착수·검수·병합을 관리한다. 아래는 후속 구현 패키지 계획이며 이번 작업은 문서만 작성하고 커밋하지 않는다.

### 바꾸지 않을 약속

- 세 주민 각 6개, 이번 연결 18개. 전체 측정 38개·별도 타이브레이커 4개를 유지한다. `id/segment/kind/axis/npc/picks/w/values`, 선택지 a→b 순서, 주민별 01→06 순서를 바꾸지 않는다. 가중치·기대 답·보상 수치는 퀘스트 파일에 복사하지 않는다.
- 프롤로그·막간·축제의 NPC 기대 답변 없는 14문항은 그대로 둔다. 돕는 주민이 등장해도 측정 상대는 원래 공략 주민이다. 심부름 완료 보상은 기존 정책의 담당 주민 +8을 한 번 적용하며 추가 보상은 없다.
- 에피소드는 자유 순서다. 완료 수에 따라 막간 1·2·3, 네 번째 완료 뒤 축제로 간다. 다른 주민을 먼저 만났어야 진행되는 조건을 만들지 않는다.
- 의도를 두 문구로 먼저 고르고 서버 확정 뒤 행동한다. 걸은 길, 터치한 위치, 속도, 실수, 힌트·자동 완성으로 답을 추정하거나 호감도를 바꾸지 않는다.
- 반응은 서버가 정한 공감/생각 두 종류다. 선택 전 선호·표정·색으로 답을 유도하지 않고 하트는 에피소드 종료에만 모아 보여준다. 플레이어 문구에 성향 축·코드·성향 수치·호감도 숫자·금지된 상표명을 넣지 않는다.
- 먼 대상 탭은 자동 접근 후 실행, Space·Enter·E 유지, 이동 조작부는 조작할 때만 표시한다. 가로 화면·회전 복구·화자 우선 카메라와 배율을 유지한다. 살펴보기 실행 버튼을 되살리지 않는다.
- 환경은 파스텔, 인물 대표색은 식별 가능하게 유지한다. 결말의 기억과 마을 정체는 암시만 남긴다. 퍼즐 30~60초·힌트·자동 완성과 축제 뒤 함께 마무리할 한 사람·고백 이유 직접 선택은 이미 결정됐으므로 다시 묻지 않는다.
- 기존 로컬 체험은 삭제하거나 서버 기록으로 가져오지 않는다. 행동형 심부름은 새 서버 회차에 연결한다. 로컬 회차는 기존 흐름을 보존한다.

**범위:** 세 주민의 생활 문제, 그 사이 쉬는 장면과 축제로 넘어가는 짧은 연결 대사, 돕는 주민의 역할 대사까지다. 막간·축제의 새 행동 퍼즐, 축제 편들기 보상 구현, 고백·결과 카드, 공식 결과 저장, 새 실내 씬·물리 운반·가방·외부 의존성은 이번 구현 묶음에 넣지 않는다. 로드맵 4단계와 저장 환경 작업에 인계한다.

## 2. 세 주민이 공유하는 플레이 원칙

목표는 한 줄, 손에 든 물건은 한 개만 표시한다. 목표를 누르고 걸어가 집기·전하기·배치하기를 실행한다. 측정 선택을 확정한 뒤에는 그 선택의 행동만 활성화한다. 다른 선택의 소품에 닿아도 답은 바뀌지 않는다. 먼 길을 잘 찾았다는 이유로 보상하지 않는다.

운반은 명시한 출발점·목적지·고정 임시 받침대만 쓴다. 자유 좌표 드롭이나 버리기는 없다. 잠시 놓았으면 ‘물건 다시 집기’가 목표가 되고 다른 운반을 시작할 수 없다. 서버가 확인한 물건 위치와 단계로 재개하며, 좌표는 저장하지 않고 해당 단계의 안전 접근점에서 시작한다. 배달 도중 앱을 닫아도 물건을 새로 만들지 않는다.

주요 퍼즐은 주민마다 하나다. ‘힌트’, ‘자동으로 마치기’, ‘잠깐 닫기’를 처음부터 같은 위치에 둔다. 힌트는 현재 퍼즐의 다음 유효한 한 조각만 알려 주며 측정 선택의 뜻이나 선호를 설명하지 않는다. 자동 완성은 서버가 남은 정답을 채운다. 닫기·재개는 확정 배치를 유지한다. 실패 종료·시간 제한·최소 대기 시간·완료 등급은 없다. 같은 답 로그라면 수동·힌트·자동 완성 모두 같은 성향·가치·호감도 결과다.

조각 선택→자리 선택 방식으로 드래그를 강요하지 않는다. 모양·짧은 이름을 함께 제공하고 색만으로 구별하지 않는다. DOM 버튼 48px 이상, 본문 대비 4.5:1, 키보드 초점과 글자 확대를 유지한다. 대사·작업판·저장 대기·회전 안내 중 이동과 자동 이동을 멈추고, 닫기 입력이 뒤의 월드까지 전달되지 않게 한다.

각 에피소드 약 4.5분, 퍼즐 30~60초는 실측할 목표다. 초과하면 비측정 왕복·연출부터 줄이고 측정 상황과 두 선택의 뜻은 줄이지 않는다. 분기별 필수 행동 수·동선 부담·힌트 접근성을 비슷하게 맞춘다.

## 3. 루미 — 바람에 빈 축제 자리 채우기

**경험:** 천막에서 손을 보태고 → 공연 카드를 놓고 → 마을에 시작 시각을 알리고 → 부족한 장식을 가져와 걸고 → 손님을 맞고 → 행진곡 악보를 전한다. 장식·공연·환영 준비가 눈에 보이게 남는다. 아직 축제 본행사를 시작하지 않는다.

| 흐름 | 플레이어가 하는 일 / 목표 문구 | 완료를 확인하는 행동 |
| --- | --- | --- |
| 천막의 부탁 | 루미와 이야기하고 조용한 탁자 또는 여럿의 자리로 간다. ‘장식 만들기’ | 선택한 자리에서 리본 묶기 또는 꽃줄 엮기 한 번 |
| 공연 준비 | ‘공연 카드 놓기’ | 선택한 공연 카드를 공용 무대 계획판에 놓기 |
| 소식 전달 | 나팔 또는 안내문 묶음을 들고 장터의 짧은 동선을 돈다. ‘축제 소식 전하기’ | 대면은 주민 두 지점에서 인사, 문서는 게시판·우편함 두 지점에 전달. 순서와 도착 기록을 단계로 저장 |
| 부족한 장식 | 무대지기가 빈 기둥을 보여 주고 루미가 보충 방법을 묻는다. ‘장식 재료 가져오기’ | 창고의 작년 리본 또는 들판의 솔방울·잎 묶음을 집어 무대 작업대에 전달 |
| 장식 걸기 | ‘표식에 맞춰 장식 걸기’ | 아래 퍼즐 완료 후 무대 기둥에 해당 재료 장식 표시 |
| 손님맞이 | ‘손님 맞이하기’ | 안내판 옆 엽서 건네기 또는 광장 인사 한 번. 손님 수·호응은 채점하지 않음 |
| 복귀와 행진곡 | 루미에게 돌아와 악보를 고른다. ‘행진곡 악보 전하기’ | 악사 받침대에 악보를 전달한 뒤 가까이 있는 루미에게 완료 보고 |

### 측정 문항을 붙일 행동 지점

아래 두 열은 원문 선택지다. 표의 ID·kind는 개발 연결용이며 화면에 표시하지 않는다. 상황도 원문을 유지하고 임시 화자 표기만 확정된 표시 이름으로 치환한다.

| ID / kind | 선택을 확정할 때 | a 원문 → 확정 뒤 행동 | b 원문 → 확정 뒤 행동 |
| --- | --- | --- | --- |
| `lumi_01` / dialogue | 천막에서 맡을 일을 묻는 순간 | 한쪽 탁자에서 내가 맡은 장식 리본을 조용히 묶을게 → 개인 탁자 작업 | 여럿이 모여 담소 나누며 꽃줄을 엮는 자리로 갈게 → 함께 쓰는 탁자 작업 |
| `lumi_02` / dilemma | 두 공연 기획 카드를 함께 보여 준 뒤 | 올해 처음 선보이는 색채 그림자극을 무대에 올리자 → 새 그림자극 카드 놓기 | 해마다 이맘때면 열던 전통 등불극을 올해도 이어 가자 → 전통 등불극 카드 놓기 |
| `lumi_03` / errand | 안내문과 나팔을 함께 건네기 전 | 장터 골목을 돌며 마주치는 주민들에게 직접 말을 건넨다 → 나팔 들고 인사 지점 둘 방문 | 마을 게시판과 우편함을 돌며 안내문을 붙여 알린다 → 안내문 들고 게시판·우편함 방문 |
| `lumi_04` / errand | 무대 기둥 꽃줄 한 묶음이 모자란 장면 | 회관 창고에서 작년에 썼던 익숙한 리본 장식을 가져온다 → 창고 수령·운반 | 들판의 솔방울과 잎을 주워 색다른 장식을 새로 엮는다 → 들판 채집·운반 |
| `lumi_05` / dialogue | 장식 완료 뒤 환영 방식을 묻는 순간 | 입구 안내판 옆에서 환영 엽서를 건네며 조용히 맞이할게 → 입구 맞이 | 광장 한복판에서 밝은 목소리로 인사하며 손님을 모을게 → 광장 맞이 |
| `lumi_06` / dilemma | 복귀 후 악사들이 두 악보를 펼친 장면 | 악사들이 오늘 처음 연주하는 경쾌한 신곡으로 시작하자 → 신곡 악보 전달 | 귀에 익어 편안한 마을의 옛 행진곡으로 시작하자 → 옛 악보 전달 |

`lumi_02`·`lumi_06`의 가치 태그도 원본 그대로다. 개인 탁자가 더 쉽거나 여럿의 자리가 더 빨리 끝나는 차이를 만들지 않는다. 대면 소식은 실제 주민에게 말을 건네며 문서 전달은 실제 게시판·우편함에서 처리한다. 둘을 같은 상자 누르기로 축소하지 않는다.

### 주요 퍼즐: 장식 고리 맞추기

`lumi_04`의 재료 전달 **뒤**, `lumi_05` **앞**에 둔다. 새 측정 문항이나 `puzzle_pre/post` 태그를 만들지 않는다. 줄 끝에 달린 동그라미·세모·네모 고리 각 두 개를 같은 표식의 여섯 자리에 잇는다. 선택한 재료는 리본 장식/솔방울·잎 장식 외형만 다르고 고리 규칙은 같다. 같은 모양끼리 숨은 순서는 없다. 틀리면 조각을 유지하고 표식을 다시 볼 수 있게 한다. 도구 없이도 현재 판만 보고 해결할 수 있다.

무대지기(`s1j2`)는 재료 받침대와 고리를 설명한다. “빈 고리는 이쪽에 있어요.”처럼 일만 안내하며 어느 재료가 루미 마음에 드는지는 말하지 않는다. 루미의 질문·반응을 대신하지 않는다.

### 주요 퍼즐: 책 표식과 자리 맞추기

`echo_04` 뒤 책 여섯 권을 같은 주제 표식의 빈 자리 여섯 곳에 놓는다. 예를 들어 식물·요리·별 이야기 각 두 권이며 표지에 주제 그림과 짧은 설명, 자리에는 같은 그림·이름을 둔다. 외부 지식 퀴즈가 아니다. 같은 주제 두 권의 내부 순서는 없다.

새 배치는 색감과 주제를 묶은 전시 외형, 기존 배치는 오래 쓰던 서가 외형으로 구별한다. 양쪽 모두 같은 표식·조각 수·탭 수·힌트를 쓴다. 새 배치만 암기하거나 기존 배치만 글을 더 읽게 하지 않는다. 완료 뒤 책 정리인(`t1p2`)이 옛 이야기책을 발견하고 에코가 함께 읽는다. 에코가 원격으로 질문하는 어색함을 피하도록 열람대에 잠깐 합류한다.

역사 서가와 별관 다락은 다른 공간이라는 원문을 유지한다. 야외의 똑같은 책더미 두 개로 대체하지 않는다. 새 실내 대신 기존 도서관 바깥의 두 접근점에서 문·서가 작업판을 여는 표현을 추천하며 §8에서 범위를 확인한다.

### 주요 퍼즐과 짧은 도면 행동을 구분한다

**주요 퍼즐:** `or_02` 모래 전달 뒤, `or_03` 앞의 시계탑 톱니 연결이다. 시계탑에서 정비하려고 내려놓은 연결판에 빠진 연결 톱니 세 개를 맞춘다. 각각 동그라미·세모·네모 축 구멍과 이름으로 구별하고, 판의 같은 축 표식에 놓는다. 톱니가 모두 들어가면 이어진 경로가 천천히 움직인다. 기어 비율 계산·회전 타이밍·물리 시뮬레이션은 없다. 수동·자동 어느 쪽이든 완료 후에만 추 선택을 연다.

**별도 행동:** `or_04`는 시계탑 퍼즐의 사전 질문으로 앞당기지 않는다. 원문대로 복잡한 톱니 도면을 보여 주되 별도 등불 승강 장치라고 설명한다. 답 확정 뒤 같은 도면의 강조된 이음 한 곳을 연결하는 짧은 조작만 둔다. 함께 검토할 때 오르가 실제로 옆에 합류하고, 혼자일 때 조용히 기다린다. 이 행동도 힌트·자동 연결이 가능하고 결과는 측정하지 않는다. 두 번째 30~60초 퍼즐이나 추가 문제를 만들지 않는다.

공방 조수(`s2j2`)는 연결판·등불 걸이를 건네고 받는 역할이다. 낚시꾼·상인은 같은 기존 보조 인물 모델을 역할별 배치에 재사용하되 대사가 실제 두 역할을 드러내게 한다. 공방 조수가 오르의 동행·반응을 대신하지 않는다.

마지막 b 분기에서 종을 전한 뒤 다시 대장간까지 왕복시키지 않는다. 오르가 광장 받침대에 합류해 보고를 받으며 완료 대상의 내부 ID는 계속 `D`다. a 분기에서는 대장간에서 보고한다. 조용히 정리한 경우 종은 주민들이 나중에 옮긴다는 연결 대사만 두어 축제가 막히지 않게 한다. 두 분기 모두 동일 보상이며 a에도 억지로 운반을 시키지 않는다.

## 6. 모카 구조 재사용과 서버 계약

### 판단: 주민별 계약 + 기존 공용 처리

| 방법 | 장점 | 이번 범위의 비용 / 판단 |
| --- | --- | --- |
| 범용 심부름 엔진: 단계 JSON을 해석해 모든 전이 실행 | 주민 추가 때 코드 중복을 줄일 가능성 | 다회 운반·분기 후 동작·퍼즐 전후 질문·복귀 위치를 표현할 조건 언어가 필요하다. 검증·디버깅·모카 이전까지 커진다. **이번에는 만들지 않음** |
| 모카의 UI·통신·서버·저장 전체를 주민마다 복제 | 처음 복사하기는 빠름 | 중복 처리·인증·재개 오류를 네 군데 고쳐야 한다. **채택하지 않음** |
| 주민별 상태·전이를 명시하고 공용 저장 경로 사용 | 각 주민의 순서가 코드와 fixture에서 바로 보임. 검증된 저장 경계 유지 | 세 전이 함수의 작은 중복을 허용한다. **추천안** |

공통 엔진을 새로 만드는 대신 이미 있는 `Engine.Apply`, `Game.command`, `sendCommand`, `savePending/loadPending`, `findPath/followPath`, 부분 계산 `Progress`, 저장소 Update 경로를 그대로 쓴다. 인증·영수증·revision·최초 답 확정 코드를 복제하지 않는다. 제작 중 반복이 실제로 생기면 모양 맞추기의 입력 표시 정도만 작은 함수로 공유한다. 퀘스트 플러그인 등록부·조건식 언어·범용 인벤토리·이벤트 버스는 필요 없다.

### 최소 상태와 명령

후속 계약 파일은 `content/quests/lumi-errand.json`, `echo-errand.json`, `or-errand.json`이다. 각 파일은 기존 여섯 문항 ID, 단계별 대상·목표 키·재개점, 선택별 행동 대상, 퍼즐 조각과 자리만 가진다. 점수·NPC 기대 답변·번역 문장은 넣지 않는다. 실제 단계 전이는 TS 참고 함수와 Go 주민별 함수로 명시한다.

- `client/src/core/play.ts`로 공용 `Pick`, `Choice`, `Command`, `PlaySnapshot`, `PendingCommand`, `LocalSync`, `contentVersionMatches`만 이동한다. `MokaState/MokaView`와 모카 전이는 기존 파일에 남긴다. 모든 import 호출자를 함께 변경하고 통신 형식은 유지한다.
- 스냅샷의 `moka`를 지우거나 이름 바꾸지 않고 `lumi`, `echo`, `or` 상태를 추가한다. 새 버전의 회차에서는 세 상태를 모두 필수로 보내고 `locked`·초기 물건 위치·빈 배치·완료 시각 `null`로 시작한다. 각 주민 상태는 고유 `phase`, 물건별 고정 위치를 담는 `objects`, 퍼즐의 `placements`, `completedAt`만 가진다. 유효 물건 ID와 위치는 각 계약의 닫힌 목록이다. 들고 있는 물건은 `objects` 중 위치가 `player`인 하나로 계산한다. 한 번에 두 개가 들린 상태는 거부한다. 이미 진행 단계가 증명하는 작업에 별도 완료 불리언을 쌓지 않는다.
- 새 `place_piece { pieceId, slotId }`만 추가한다. 허용 퍼즐·조각·자리는 서버의 현재 주민·단계로 결정하고 요청의 `questId`, 완료 배열, 다음 단계는 받지 않는다. 모카 `place { breadId, slotId }`와 기존 fixture는 유지한다. `auto_arrange`는 현재 주민의 열린 퍼즐에만 허용한다. 도면의 짧은 연결은 기존 `act`로 처리한다.
- `pickup/set_down/deliver/act/talk/complete`는 기존 `targetId` 형식을 재사용한다. 대상 ID는 `lumi-`, `echo-`, `or-` 접두로 충돌을 막고, 보고 대상은 기존 `A/C/D`다. 임시 받침대는 주민당 하나(`lumi-rest`, `echo-rest`, `or-rest`)이며 현재 운반 물건만 내려놓고 다시 집을 수 있다.
- 이름·길·배치 방식·마무리 방식은 확정 답에서 파생한다. `lumiView(snapshot)`, `echoView(snapshot)`, `orView(snapshot)`는 `objectiveKey`, `activeTargetIds`, `resumePointId`, 운반 표시·배치·해당 주민 분기를 반환한다. 월드는 같은 값으로 표시하고 새 답을 계산하지 않는다. `Village.setLumiView`, `setEchoView`, `setOrView`로 명시적으로 연결한다.

**주민별 전이 순서:** 아래 화살표 사이의 물건·대상 확인이 끝나야 다음 선택으로 간다. 각 행동은 취소 없이 서버에 확인되는 한 명령이며, 실패하면 상태를 변경하지 않는다. 실제 단계 ID와 각 대상 ID는 계약 패키지가 아래 순서대로 고정한다.

### 공통 완료·재전송·버전의 연결

1. `Engine.Apply`가 현재 구간을 정확히 구분해 주민별 전이로 보낸다. 세 신규 주민에서도 `finish_segment`를 거부한다. 프롤로그·막간·축제·문은 기존 전환을 유지한다. 모카를 새 상태 엔진으로 이식하지 않는다.
2. 완료 시 `{주민}-errand-completed` 고정 사건, `CompletedErrands`, 완료 에피소드, 서버 시각, 다음 막간/축제를 기존 저장 갱신 안에서 한 번 기록한다. 점수는 기존 `Progress`와 완료 보상 규칙으로 계산한다. 모카 완료 여부만 보고 다른 주민의 `complete`를 처리하지 않는다.
3. HTTP의 `B` 전용 재완료 판정을 고정 대상 `A/B/C/D`→각 주민 사건 매핑으로 확장한다. 같은 키·같은 요청은 원래 영수증, 같은 키의 다른 요청은 충돌, 같은 문항의 다른 답은 거부다. 다른 키 재완료와 같은 답 재전송도 revision·보상·반응을 늘리지 않는다.
4. 현행 HTTP는 의미상 중복에 원래 영수증 키를 반환하지만 클라이언트는 보낸 키와 같아야 응답을 받는다. 새 주민에 복사하지 않는다. 통합 패키지에서 **현재 요청이 같은 문항의 같은 답 또는 같은 완료인지 최신 상태로 확인한 경우만** 이전 키 영수증을 허용하고, 그 외 키 불일치는 계속 거부한다. 요청의 대기 기록은 재전송 키로 정리한다. 서버와 클라이언트를 함께 검증하는 중복 완료 회귀를 남긴다.
5. `episodeEnd`는 방금 완료한 주민의 표시 정보다. 응답 검증은 모카 완료 여부가 아니라 `npcId`에 해당하는 완료 상태·완료 목록과 하트 범위를 확인한다. 이후 응답에서 생략될 수 있고, 재완료로 새 하트 애니메이션을 만들지 않는다. 점수·기대 답은 진행 응답에 넣지 않는다.
6. `scripts/content-version.mjs`의 명시 목록에 세 퀘스트 JSON을 추가한다. 이미 포함되는 양 언어 ink·문구도 같은 빌드에서 사용한다. fixture는 테스트 자료로 구별한다. 서버 콘텐츠 로딩·배포 파일 포함·클라이언트 버전 대조를 함께 확인한다.
7. 기존 회차를 삭제하거나 이미 답한 주민을 행동 단계 처음으로 되돌리지 않는다. 새 계약은 새 버전의 서버 회차부터 사용한다. 구버전 활성 서버 회차는 호환 배포가 준비되지 않았다면 기존 `content_version_unavailable`로 보류하고 기록을 보존한다. 조용히 새 상태를 끼워 넣는 마이그레이션은 하지 않는다. 운영에서 버전별 재개를 지원하는 작업은 저장 환경 담당이 검증해야 한다.

위 4번은 코드 대조로 발견한 연결 위험이며 이번 문서 작업에서 수정하지 않았다. 별도 보안·스토리지 엔진을 만드는 이유로 확대하지 않는다. 클라이언트가 보낸 시간·이동 좌표·완료 여부는 믿지 않는다. 서버는 허용 행동 순서를 판정하며 실제로 걸었는지를 증명하지는 않는다. 현재 인메모리 API 통과를 Firebase 인증·App Check·Firestore 영속성 통과로 보고하지 않는다.

임시 후보 영역은 루미의 광장·회관 가장자리, 에코의 서쪽 도서관, 오르의 대장간 바깥·기존 물가다. 새로 필요한 개울 채집지는 물가에 작은 ‘고운 모래가 쌓인 유입부’를 시각적으로 구분한다. 시계탑 연결판과 등불 승강 도면은 서로 다른 소품·목표명으로 둔다. ‘서가/다락/시계탑/개울’이 실제로 이미 존재한다는 보고는 하지 않는다.

물건 중심과 접근점을 분리하고 기존 충돌·거리·가림·자동 이동으로 검증한다. 돕는 주민을 해당 에피소드 동안만 작업대 옆에 배치하며 종료 때 원래 위치를 복원한다. 진행 중 회전은 위치를 유지하고 새로고침은 안전 지점에서 재개한다. 완료한 장식·전시·걸이 외형은 각 주민의 서버 완료 상태에서 복원하고 다른 에피소드가 숨기거나 초기화하지 않는다. 모카 배달과 오르 작업은 어느 순서로 해도 독립적이다.

새 아트는 `assets/source/residents-errands/<주민>/`, `assets/_generated/residents-errands/<주민>/`에 원본·제작 근거·미리보기·크기/충돌 정보를 둔다. 승인 산출만 `client/public/assets/abraxas/environment/prop-lumi-*.glb`, `prop-echo-*.glb`, `prop-or-*.glb` 및 필요한 `ui/residents-errands/`로 낸다. 기존 모카 GLB를 덮어쓰지 않는다. 해당 에피소드 진입 때 준비하고 T013 첫 끊김 개선을 유지한다. 초기 용량·드로 콜·기기 성능 예산은 기존 기준을 사용하며 이번 문서에서 통과를 주장하지 않는다.

### 구현 패키지: 독점 파일과 순서

각 패키지는 별도 브랜치·worktree·PR 목적 하나로 다룬다. `<npc>`는 `lumi/echo/or`, `<lang>`은 `ko/en`이다. 공용 파일의 소유권은 **순차 이전**하며 표에 없는 파일이 필요하면 감독에게 소유권 배정을 요청한다. 구현·아트 작업자는 커밋하지 않는다.

## 9. 이번 계획 작업의 검증과 감독 인계

이번에는 이 문서만 작성한다. 제품 코드·측정 데이터·정책·에셋은 수정하지 않고 git commit도 하지 않는다. `.agents/rules/delegation.md`의 위임 작업자 규칙에 따라 공용 `docs/memory/`·`docs/devlog/`는 직접 수정하지 않는다. Claude에게 인계할 상태는 **RS1 계획 작성·사람 검토 대기**, 새로운 사람 확정 결정은 없음이다. 추천안을 확정 결정으로 기록하지 않는다.

문서 검증과 실제 제품 검증을 구별한다. 현재 작업에서 `npm run check:scoring`은 38문항·타이브레이커 4개로 통과했다. Go vet/test의 첫 시도는 기존 캐시 접근 거부였으며, 명령 프로세스의 `GOCACHE`만 쓰기 가능한 임시 경로로 지정해 재실행한 `go vet ./...`와 `go test ./...`는 통과했다. 클라이언트 typecheck/test는 `tsc`·`vitest` 부재로 실행되지 않았고, `govulncheck`도 명령 부재다. 의존성 설치·환경 배포는 하지 않는다.
