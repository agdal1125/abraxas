# 마지막 산책과 근거 있는 결과 카드 구현 계획

상태: 사람 승인, 구현 중 (2026-11-07). 결정 1~3은 권고안으로 확정했다.

## 왜 하는가

Abraxas의 차별점은 자기 이해다. 플레이어는 자기 말이 NPC를 바꿨음을 체감하고, 좋아하는 사람을 고르고, 결과에서 자신을 돌아봐야 한다.

지금 코드는 이 경험을 충분히 주지 못한다.

- 플레이 중 NPC 반응은 공감과 생각에 잠김 두 가지뿐이고, 달라진 모습을 보여 주는 장면이 없다.
- 결과 카드 `그 사람`은 고백 대상의 최종 성향만 보여 주고, 처음과의 차이를 보여 주지 않는다.
- 결과 카드 `나`는 판정의 근거를 보여 주지 않는다. 기획서의 `내가 지킨 가치 TOP 3`도 빠져 있다.

## 무엇을 바꾸는가

1. 기억의 문 뒤, 고백 전에 네 사람의 달라진 모습을 보여 주는 `마지막 산책`을 넣는다.
2. 결과 카드 `그 사람`에 처음과 지금의 차이를 넣는다.
3. 결과 카드 `나`에 가치 TOP 3와 `그렇게 본 순간` 보기를 넣는다.

측정 문항, 가중치, NPC 이동 폭, 호감도, 유형 판정, 서버 API, Go 코드는 바꾸지 않는다. 결과 카드는 3장을 유지한다. 호감도 규칙은 별도 결정으로 남긴다(결정 3).

## 측정을 오염시키지 않는 이유

마지막 산책은 타이브레이커 4문항까지 모두 답한 뒤에 나온다. 그래서 이번 회차의 측정에는 영향을 줄 수 없다. 고백 대상 선택은 원래 측정하지 않는다.

재플레이에서는 플레이어가 NPC 변화와 판정 근거를 이미 안다. 측정 순도가 낮아질 수 있지만, 1회차 결과를 `처음의 나`로 따로 보관하는 현재 규칙이 이 위험을 막는다.

`그렇게 본 순간`은 공유 문구에 넣지 않는다. 어떤 선택이 어떤 결과로 이어지는지 공유되면, 아직 플레이하지 않은 사람의 1회차가 오염될 수 있다.

## 데이터 모델

표시 전용 계산을 `client/src/core/reflection.ts`의 순수 함수 하나로 모은다.

```ts
type NpcShift = "deepened" | "steady" | "wavering" | "turned";

type Reflection = {
	npcChanges: Record<EndingNPC, { axis: MainAxis; shift: NpcShift }[]>;
	moments: { axis: MainAxis; itemId: string; pick: string; boundary: boolean }[];
	topValues: string[];
};
```

입력은 서버가 확정한 답 로그와 콘텐츠 데이터다. 결과는 저장하지 않고 화면을 열 때 계산한다. 그래서 다시 불러와도 같은 값이 나오고, 저장 형식과 서버 계약도 그대로다.

이 계산은 표시에만 쓴다. 유형과 고백 결과는 지금처럼 서버 값을 쓴다.

`progress()`는 NPC 성향과 호감도만 돌려주므로, 플레이어 점수 `s`도 함께 돌려주도록 고친다. `s`에는 타이브레이커 가중치가 들어가지 않아 경계 구간 판정(`|s| < 10`)에 그대로 쓸 수 있다. 데이터 타입에는 `npcs.json`의 `themeAxes`를 추가한다.

### NPC 변화 단계

주제 축은 NPC마다 2개, 축마다 3문항이다. 시작값이 ±30이고 이동 폭이 20이므로, 시작 극 기준 최종값은 네 가지뿐이다. 계산 스크립트로 8가지 선택 조합을 모두 확인했다.

| 시작 극 기준 최종값 | 시작 극과 다른 선택 수 | `shift` | 이름 |
| --- | --- | --- | --- |
| 90 | 0 | `deepened` | 더 단단해짐 |
| 50 | 1 | `steady` | 그대로 |
| 10 | 2 | `wavering` | 흔들림 |
| -30 | 3 | `turned` | 달라짐 |

`shift`는 `(시작 극 기준 최종값 - 30) / npcStep`의 결과 +3, +1, -1, -3으로 구한다. 기준은 `progress()` 하나다.

### 그렇게 본 순간

주축마다 한 순간을 고른다.

1. 경계 구간 축이면 그 축의 타이브레이커 선택을 쓰고 `boundary`를 켠다.
2. 그 밖의 축이면 그 축이 주 적재 축인 문항 중 결과 극과 같은 쪽 선택을 찾는다. 가중치가 가장 큰 선택을 쓰고, 같으면 나중에 고른 선택을 쓴다.
3. 그런 선택이 없으면 타이브레이커 선택을 쓴다. 보조 적재 축만으로 극이 정해진 경우다.

화면에는 플레이어가 실제로 본 선택지 문구를 쓴다. 한국어는 `items.json`, 영어는 `content/i18n/en/items.json`에서 읽는다. `check-dialogue.mjs`가 두 파일과 ink 문구의 일치를 이미 검사한다.

### 가치 TOP 3

딜레마 9문항의 `values`를 센다. 9문항뿐이라 동점이 자주 나올 수 있다. 동점이면 나중에 고른 가치를 앞에 둔다. 영어 표시용으로 10가치의 번역을 `ui.json`에 추가한다.

## 화면

### 마지막 산책

`Game.ending()`에서 `demi_reveal` 뒤, `confession_intro` 앞에 넣는다. 고백을 이미 마쳤으면 건너뛴다. 새 segment와 서버 상태를 만들지 않으므로 새로고침하면 다시 재생될 뿐이다.

네 사람이 한 명씩 말한다. NPC마다 변화가 가장 큰 축을 하나 고른다. 우선순위는 `turned`, `wavering`, `deepened`, `steady`이고, 같으면 `themeAxes` 순서를 따른다.

대사는 `content/ink/{ko,en}/last_walk.ink`의 `walk_<npc>_<axis>_<shift>` 노트에 둔다. 8개 축 × 4단계 × 2개 언어로 64개 노트다.

대사 규칙은 다음과 같다.

- 2줄 이내로 쓰고 인물별 말투 규칙을 따른다.
- 축 이름, 수치, 유형 이름을 쓰지 않는다.
- 어느 단계도 더 낫다고 말하지 않는다. `turned`를 칭찬이나 성공으로 쓰지 않는다.

루미의 A축 대사 예시는 다음과 같다.

| 단계 | 예시 |
| --- | --- |
| `deepened` | 역시 다 같이 있을 때 제일 신나! |
| `steady` | 오늘도 같이 있어서 좋았어! |
| `wavering` | 가끔은 조용한 시간도 괜찮더라. |
| `turned` | 오늘은 나도 혼자 걷고 싶어졌어. 신기하지? |

### 결과 카드 `나`

네 줄 설명 아래에 TOP 3를 한 줄로 넣는다. `그렇게 본 순간` 버튼을 누르면 같은 카드 안에서 네 순간을 보여 주고, 돌아가기로 복귀한다.

경계 구간 축에는 "두 모습이 모두 보였어요"를 함께 쓴다. 고지 문구는 그대로 둔다. 공유 문구에는 TOP 3까지만 넣는다.

### 결과 카드 `그 사람`

주제 축 2개를 단계별 문장으로 보여 주고, 닮은 점과 다른 점, 성찰 문구는 유지한다.

| 단계 | 문장 틀 |
| --- | --- |
| `deepened` | 〈시작 극〉 마음이 더 깊어졌어요. |
| `steady` | 여전히 〈시작 극〉 사람이에요. |
| `wavering` | 〈시작 극〉 사람이지만, 〈반대 극〉 마음에도 귀를 기울이게 됐어요. |
| `turned` | 처음엔 〈시작 극〉 사람이었지만, 지금은 〈반대 극〉 쪽에 가까워졌어요. |

〈〉에는 `ui.result.poles`의 문구를 넣는다.

## 작업 순서

PR 하나에 목적 하나만 담는다. PR 1이 끝나면 나머지 둘은 서로 다른 화면을 고치므로 병렬로 진행할 수 있다.

1. **계산 코어.** `reflection.ts`, `progress()` 반환값, `themeAxes` 타입을 추가한다.
2. **마지막 산책.** `last_walk.ink` ko/en과 `Game.ending()` 연결을 추가하고 대사를 검수한다.
3. **결과 카드.** `나`와 `그 사람` 카드, `ui.json` ko/en을 고친다.
4. **호감도.** 불일치 호감도 +4를 TS·Go·골든에 반영한다.
5. **문서.** `game-design-policy.md`에 공유 제외 규칙을 추가하고, 기획서 플레이 시간, 시나리오 문서, `docs/memory/`, `docs/devlog/`를 갱신한다. 정책 추가는 이 계획의 승인으로 본다.

## 검증

공통으로 `npm run typecheck && npm test`를 통과해야 한다. 서버 코드는 바꾸지 않지만, 공유 콘텐츠를 건드리므로 `go vet ./... && go test ./... && govulncheck ./...`와 `npm run check:scoring`도 돌린다.

| 대상 | 확인할 동작 |
| --- | --- |
| `shift` | NPC 4명 × 축 2개 × 8가지 조합 전부에서, `turned`와 최종 유형 글자가 뒤집힌 경우가 정확히 일치한다 |
| 순간 선택 | 무작위 전체 로그에서 주축마다 항상 한 순간이 나오고, 그 선택이 실제 답과 결과 극에 맞는다 |
| 대사 | 64개 노트가 모두 있고, 금지어와 길이 검사를 통과한다 |
| 흐름 | `npm run e2e:play`의 ko/en 전체 플레이에서 산책, 고백, 카드 3장을 지나며, 산책 중 새로고침해도 답과 결과가 바뀌지 않는다 |
| 공유 | 공유 문구에 `그렇게 본 순간`이 들어가지 않는다 |
| 화면 | 게임 크기 740×360에서 카드 두 장과 순간 보기가 잘리지 않는다. 글자 크게 20px도 확인한다. 실기기 확인은 별도로 남긴다 |

## 정해야 할 것

### 결정 1. 산책 방식

권고는 **순서대로 재생**이다. 먼저 만들어 실제로 플레이해 보고, 영상처럼 수동적으로 느껴지면 자유 이동으로 바꾼다. 자유 이동은 더 느긋하지만 목표 표시, 이동 안내, 재개 처리가 늘어난다.

### 결정 2. 플레이 시간

산책은 약 1분이 걸리므로 1회 플레이가 31분에서 약 32분으로 늘어난다. 권고는 **32분으로 수용**이다. 시간은 측정 수치가 아니고, 줄일 곳을 찾느라 측정 문항이나 심부름을 건드릴 이유가 없다.

### 결정 3. 호감도 규칙

이번 범위에서는 호감도를 바꾸지 않는다. 다만 산책으로 변화가 눈에 보이면 다음 문제가 더 두드러진다. 지금은 NPC에게 많은 변화를 준 플레이어일수록 고백이 `waiting`으로 끝나기 쉽다.

아래 표는 심부름 보너스(+8)를 포함한 값이며, 고백 기준은 60이다. 축제 동행자는 여기에 +10을 받는다.

| 불일치 시 호감도 | 두 축 모두 `turned` | 가장 낮은 경우 (두 축 모두 불일치 3회) | 의미 |
| --- | --- | --- | --- |
| 0 (현재) | 52 | 28 (동행 시 38) | 변화를 많이 줄수록 거절되기 쉽다 |
| +4 | 68 | 52 (동행 시 62) | 변화를 준 관계도 대체로 이어진다 |
| +6 | 76 | 64 | 항상 성공해 기준이 의미를 잃는다 |

권고는 **+4를 별도 PR로 진행**하는 것이다. 정책 수치 변경이므로 승인이 필요하고, TS·Go·골든 테스트를 함께 고쳐야 한다. `scoring-change` 스킬 절차를 따른다.

## 범위 밖

- 벤치에 앉기, 쓰다듬기 같은 휴식 행동
- 소리와 챕터별 빛 변화
- 재플레이에서 `처음의 나`와 근거 비교
- 초대권과 광고 구조 재검토
