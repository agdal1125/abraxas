## 비평을 측정 가능한 문제로 바꾸기

비평의 표현을 그대로 받아쓰지 말고, 첨부 화면과 코드에서 원인을 확인해 원인별로 적는다. 감독이 본 후보는 다음과 같다. 맞는지 직접 확인하고, 틀리면 틀렸다고 적고, 빠진 것을 더한다.

| 비평 | 감독이 본 후보 원인 |
| --- | --- |
| 길 모서리가 집보다 날카롭다 | 길이 꺾인 다각형이고 가장자리만 흐리다. 길에 폭 변화·돌·풀 침범·바퀴 자국이 없다 |
| 집이 블록 장난감 같다 | 벽이 빈 면이고 창문이 거의 없다. 지붕은 단색 평면이고 기와·처마 두께·굴뚝 연기가 없다. 큰 천과 노란 곡면이 무엇인지 안 읽힌다 |
| 느낌표가 구조 요청 같다 | 평면 원 UI가 3D 세계에 떠 있고 세계와 연결되지 않는다 |
| 하얀 유령, 지우다 만 자리표시자 | 알 껍질 주인공의 정점 색을 모두 흰색으로 덮어 AO와 껍질 경계가 사라진다(`whitenPlayer`) |
| 저폴리 연옥 | 지면이 단색 평면, 같은 상자·통나무·꽃의 균일한 반복, 평평한 조명, 시점의 이유가 없는 빈 공간 |

## 정책에 담을 내용

1. **목표 인상.** 무엇으로 보여야 하는지 한 문단으로 정한다. 측정 무결성, 성별 중립, 약 3등신, 선명한 대표색, 얼굴 없는 알 껍질 주인공, 정사영 쿼터뷰를 유지하는지 또는 바꿔야 한다면 왜인지를 명시한다. 특정 게임의 이름·캐릭터·에셋·외관을 복제하지 않는다.
2. **그래픽 방향 후보 2~3개 비교.** 예: 저폴리를 유지하고 재질·조명·밀도로 끌어올리기 / 손그림 텍스처 입히기 / 아트 전면 교체. 후보마다 인상, 비용, 모바일 성능 영향, 기존 GLB·생성기 재사용 범위, 실패 위험을 표로 적고 **하나를 추천**한다. 어느 쪽이든 현재 Blender 절차형 파이프라인이 그 품질을 낼 수 있는지 정직하게 판단한다.
3. **판정 가능한 규칙.** 지면·길, 건물, 소품 반복, 나무·식생, 조명·그림자, 하늘·안개·시간 변화, 주인공, 진행 표식, 카메라, UI별로 규칙을 쓴다. "예쁘게" 같은 말 대신 다음처럼 검사할 수 있게 쓴다. 건물은 게임 크기에서 용도가 이름표 없이 읽힌다, 같은 소품이 한 화면에 N개 넘게 같은 각도로 나오지 않는다.
4. **플레이 몰입 규칙.** 그래픽만이 아니라 플레이 감각을 다룬다. 이동의 손맛, 세계 반응(걸으면 생기는 것, 말을 걸면 달라지는 것), 소리, 시간 흐름, 탐색 보상, 표식 없이도 길을 찾는 환경 유도, 장면 전환. 30분 체험과 모바일 조작에 맞는 것만 고른다. 측정 무결성 정책을 어기는 것(기대 답변 암시, 선택별 평가성 반응, 숨은 점수 변화)은 금지 목록에 적는다.
5. **예산.** `docs/reviews/perf-mobile-2026-11-01.md`와 현재 값을 근거로 삼각형, 재질, 텍스처, 전체 용량, 프레임 목표를 적는다. 측정하지 않은 값은 미측정이라고 적는다. 지금 값이 없으면 측정 방법을 적는다.
6. **검수 절차.** 무엇을 어떤 화면 크기로 전후 캡처하고 무엇으로 합격시키는지. 수치 검사 통과를 아트 합격으로 치지 않는다. 대표 장면 하나를 먼저 시제품으로 만들어 사람이 본 뒤 확장한다.
7. **작업 단위와 순서.** 효과가 큰 순서로 패키지를 나눈다. 패키지마다 독점 쓰기 파일, 담당(구현·아트는 agy, 한도 시 Terra), 완료 기준, 대략 규모를 적는다. 첫 패키지는 한 화면(예: 광장 또는 빵집 앞)의 시제품이다.
8. **하지 않을 것.** 이번에 하지 않을 일과 이유.
9. **사람에게 물을 질문.** 마지막 절에 결정이 꼭 필요한 질문만 적고, 각 질문에 추천안을 붙인다. 혼자 정하지 않는다.

## 근거

웹 자료를 쓰면 출처를 적고 직접 확인한 것만 쓴다. 게임 화면을 직접 돌리지 못했으면 코드·프리뷰 근거로 판단했다고 밝힌다. 측정하지 않은 성능 효과를 단정하지 않는다.
