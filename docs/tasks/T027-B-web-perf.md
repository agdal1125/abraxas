# T027-B 폰 웹 브라우저 성능 측정과 최적화

2026-11-12 · game-engineer · 기준 커밋 `c6f26b8`(main)

사람의 요청: "웹 브라우저 기반 게임이라는 점도 체크해서 최적화도 해주고". 이 문서는 잰 방법, 전후 표, 한 일, 하지 않은 일, 미측정 항목을 적는다. 실기기는 재지 못했다. 아래 시간 값은 이 PC에서 CPU를 4배로 늦춰 본 상대값이고, 부하에 안 흔들리는 값(바이트, 요청 수, 드로콜, 같은 입력의 결과 비교)을 주 근거로 삼았다.

## 측정 방법

- 도구는 `threejs-mobile-perf` 스킬의 방식을 따랐다. 스크립트는 저장소에 넣지 않았다(세션 임시 폴더). 아래 조건을 보면 다시 만들 수 있다.
- 로딩: 프로덕션 번들을 Firebase Hosting과 비슷한 정적 서버(brotli 압축, 영상 range, `/v1` 프록시)로 내리고 빈 프로필의 Chrome(헤드리스)으로 연다. 뷰포트 740×360, DPR 2, 터치. CDP `Network`로 요청과 전송 바이트(`encodedDataLength`)를 센다. 제목 화면의 "시작하기"까지, 누른 뒤 9초까지를 나눠 적었다. 측정용 번들은 `NODE_ENV=development VITE_ABRAXAS_DEV_FAKE_AUTH=1 vite build`로 만들었다(개발 훅 `window.__abraxas`와 가짜 인증이 들어가고 나머지는 프로덕션과 같다).
- 드로콜과 삼각형: `renderer.info`, `autoReset` 끄고 `renderer.render` 직접 호출, 후처리(`effects`) 미포함. 그림자 맵 갱신을 끈 값과의 차이가 그림자 pass다.
- 프레임당 JS: 같은 PC에서 두 번들을 번갈아 3회씩. CPU 4배 감속, 마을 광장에서 6초 걷기. `requestAnimationFrame` 콜백 시간, `renderer.render` 시간을 감싸서 쟀다. SwiftShader에서는 GL 호출이 GPU 대기를 품어 `render` 값이 흔들리므로, 주 값은 `tick − render`(렌더 제출 제외 JS)와 실제 GPU(D3D11, 헤드리스)에서 잰 `tick`이다.
- CPU 프로필: CDP `Profiler`, 샘플 간격 200µs, 걷는 6초. 할당: CDP `HeapProfiler` 샘플링(수거된 객체 포함), 프레임당 KB.
- 같은 PC에서 다른 작업이 캡처를 돌리고 있어 시간 값은 흔들린다. 같은 값을 3회 적어 흔들림을 보였다.

### 프레임당 JS (CPU 4배 감속)

| 항목 | 전 | 후 |
| --- | ---: | ---: |
| 렌더 제출 제외 JS, 프레임당 (SwiftShader, 3회) | 8.9 / 8.9 / 7.5 ms | 2.4 / 4.0 / 2.6 ms |
| `tick` 전체 (실제 GPU, 2회) | 6.9 / 6.7 ms | 3.3 / 2.8 ms |
| 같은 조건의 `requestAnimationFrame` 처리량 | 135~140 /s | 236~239 /s |
| 프레임당 할당 (샘플링 프로파일) | 292 KB | 134 KB |

SwiftShader에서는 장면이 GPU에 묶여 30 fps 근처이고, 줄인 CPU 시간이 `render` 안의 GPU 대기로 옮겨 가서 `tick` 전체와 fps는 달라지지 않는다. 폰에서 이득이 보이는 것은 CPU가 병목일 때(느린 폰, 열이 올라 클럭이 떨어질 때)와 GC가 끊김을 만들 때다. GPU가 병목인 폰은 아래 자동 품질 단계가 맡는다.

원인은 한 가지가 가장 컸다. 걸을 때마다(프레임당 1회 이상) `step()`이 `boundaries()`를 처음부터 다시 계산했다. 경계 선분 전부를 서로 교차시키는 O(E²)이고 입력은 변하지 않는 지도다. 프로필에서 `inside`, `boundaries`, `sub`, `cross`, `step`이 CPU 샘플의 약 15%였다.

## 한 일

1. `client/src/core/world/move.ts`: 경계 선분과 상자 모서리를 `WeakMap`으로 한 번만 계산. 충돌 검사를 할당 없는 산술로 바꾸고(`distanceToSegment`), 이동 한 걸음에서 먼 선분은 사각형 검사로 건너뛴다.
   - 같은 입력의 결과가 같은지: 실제 마을 지도와 충돌체로 무작위 걷기 12만 걸음(속도 5~55 배속 포함), 옛 구현과 새 구현의 결과가 비트 단위로 같았다(차이 0). 한 걸음 계산 시간은 324 s → 35 s(12만 걸음 합).
2. `client/src/core/world/nearby.ts`, `village.ts`의 `findNearby`: 매 프레임 모든 소품·인물에 대해 시선 검사(`visible`, 모든 충돌체 순회)와 `colliders.filter`를 하던 것을, 닿는 거리(0.95) 안인 대상만 시선 검사하도록 순서를 바꾸고 소유자별 충돌체 색인으로 바꿨다. `visible`의 상자 검사는 임시 배열을 만들지 않는다. 선택 결과는 같다: 개발 번들에서 무작위 6,000 상태(플레이어 위치, 사용 가능 집합, 이전 선택)로 옛 구현을 복사해 비교, 차이 0(결과 있음 3,870).
3. `village.ts`: 움직이지 않는 소품(`place()`)과 장면 뿌리의 행렬 갱신을 끈다. 뷰 밖(카메라 중심에서 보이는 영역 + 3 밖)인 인물은 믹서, 스프링, 행렬 갱신을 건너뛰고 돌아오면 이어 간다. 호수 식물(`water-*`)은 물이 움직이므로 뺐다. 정지 상태 검사: 어귀, 광장, 호숫가, 빵집, 마을 문, 도서관과 걷는 중에 행렬이 잠긴 노드 1,002~1,041개 모두 저장된 행렬과 로컬 변환이 같고, 갱신 중인 노드의 월드 행렬도 맞았다.
4. `spring-bones.ts`: 프레임마다 만들던 벡터를 모듈 임시 값으로. `activeTargets`, `residentActor`의 임시 배열 제거.
5. 자동 품질 단계(`client/src/scenes/quality.ts`, `village.ts`): 프레임 평균이 28 ms(약 36 fps) 넘는 창(120프레임)이 두 번 이어지면 한 단계씩 낮춘다. 단계 1: 그림자 맵을 2프레임에 한 번 다시 그린다. 단계 2: 픽셀 비율 상한 1.25. 단계 3: 픽셀 비율 1.0. 올라가지 않고, 잘 도는 기기는 단계 0에 머물러 화면이 같다. `?quality=0..3`으로 단계를 고정해 눈으로 비교할 수 있다(자동 판단은 꺼진다). 효과를 보려고 CPU를 20배 늦춘 환경에서 약 20초 만에 1, 40초에 2, 50초에 3으로 내려갔고, 정상 속도에서는 12초 동안 0이었다.
6. 인트로 영상(`.cinematic`)이 캔버스를 덮는 동안 마을 렌더와 갱신을 멈춘다. 영상 디코딩과 3D 렌더가 폰에서 같은 시간에 도는 것을 막는다. 덮개를 걷으면 바로 이어진다(확인: 덮인 2초 동안 렌더 0회, 걷은 뒤 2초 234회).
7. 빌드(`client/vite.config.ts`): `three` 전용 청크, `three`가 `dist`에 복사하는 쓰이지 않는 Draco 파일 5개 제거, 큰 청크 경고 한도 750 KB, 모델과 텍스처 URL에 붙일 `__ASSET_VERSION__`(`public/assets/abraxas` 파일 내용의 해시 10자).
8. `client/src/asset-url.ts`, `village.ts`, `dream-effects.ts`: 모든 GLB와 FX 텍스처 URL에 `?v=<해시>`.
9. `firebase.json`: 위 URL, 해시된 `assets/*.js|css`, `cinematics/**`는 `immutable` 1년, `fonts/**` 30일, HTML은 `no-cache`. 지금은 HTML이 기본 1시간 캐시라서 배포 직후 옛 `index.html`이 지워진 해시 파일을 가리킬 수 있었다.
10. 지형 GLB를 두 번 요청하던 순차 경로를 한 번의 로드로 줄였다(실패했을 때만 있는지 확인하는 요청을 보낸다). 느린 망에서 지형이 가장 늦게 오는 경우 왕복 한 번이 빠진다.

테스트: `move.test.ts`(경계와 충돌체별 캐시), `quality.test.ts`(자동 단계). 전체 `npm test` 194개 통과(CPU가 바쁠 때 한 번 시간 초과 실패가 있었고 다시 돌리면 통과했다).

## 확인한 것 (문제 없음)

- 숨은 탭: `document.hidden`이면 렌더와 갱신이 멈춘다(2초 동안 0프레임), 돌아오면 이어진다. 타이머(`setInterval`)는 코드에 없다.
- WebGL context lost: `WEBGL_lose_context`로 잃고 되살렸을 때 오류 없이 다시 그려졌다(복구 후 81 calls, 스크린샷 정상). 잃은 동안 루프는 계속 돌지만 `three`가 렌더를 건너뛴다.
- 영상은 시작 버튼 뒤에만 요청한다. `preload="none"`.

## 하지 않은 것과 이유

- **꽃·풀·조약돌 인스턴싱.** 어귀·빵집 같은 곳에서 그림자 없는 장식(꽃 클러스터, `grass-small`, 조약돌)이 그림자 제외 calls 약 58개 중 약 35개다. 인스턴싱하면 크게 줄지만, 꽃을 더 심는 들판 작업(`nature*.ts`)이 같은 곳을 바꾸고, 공간 단위로 나누지 않으면 컬링이 사라져 삼각형이 는다. 들판 작업이 끝난 뒤 그 밀도를 기준으로 다시 재는 쪽이 낫다. 바람 셰이더는 이미 `USE_INSTANCING`을 지원해서 옮기기 쉽다.
- **그림자 해상도, 픽셀 비율 기본값, `alpha: true`/`antialias` 변경.** 화면이 달라진다. 자동 단계로만 낮춘다.
- **정적 그림자 캐시.** 그림자 카메라가 플레이어를 따라 움직이고 인물이 움직여 매 프레임 내용이 달라진다. 자동 단계 1의 격프레임 갱신이 대신한다.
- **`draco` 디코더를 `gltf` 변형으로 교체**(wasm 286 KB → 192 KB, 전송 약 12 KB 차이). GLB 모두 디코드되는지 확인이 필요하고 이득이 작아 남겼다.
- **인증 청크 미리 받기**(제목 화면에서 `firebase/app`, `firebase/auth` 모듈 미리 내려받기). `main.ts`의 일이라 건드리지 않았다. 아래 넘기는 개선 참고.
- **서버, 측정, 판정, 저장 로직.** 건드리지 않았다.

## 미측정

- 실기기 FPS, 프레임 간격 p95, 발열, 메모리 증가(중급 Android Chrome, iPhone Safari, 카카오톡 인앱).
- 후처리(`effects`)를 포함한 드로콜.
- 실제 Firebase Hosting에서의 헤더 동작과 CDN 재검증.
- 느린 망(Fast 3G)에서의 제목 화면까지 시간. 로컬 서버라 지연이 거의 없다.
- 단계 1~3의 화면 차이를 눈으로 본 것: `?quality=` 고정으로 폰에서 사람이 봐야 한다.
- Firebase 인증이 켜진 실제 시작 흐름의 전송량(측정용 번들은 가짜 인증).

## 다른 담당 파일에 걸린 개선 (넘김)

- `client/src/main.ts`: 제목 화면이 뜬 뒤 `requestIdleCallback`에서 `import("firebase/app"); import("firebase/auth")`로 모듈만 미리 받으면 "시작하기" 뒤 인증 대기가 줄어든다(익명 로그인은 시작 뒤에 하므로 서버에 계정이 늘지 않는다). 제목 화면은 마을 GLB 49개를 다 받은 뒤에 나온다. 마을을 배경으로 쓰지 않는 제목이라면 먼저 띄우고 뒤에서 받는 쪽이 첫 화면은 빠르다.
- 인트로 영상 덮개: 마을 렌더 정지가 `.cinematic` 클래스를 본다. 클래스 이름을 바꾸거나 반투명으로 만들면 정지가 어긋난다. 덮개가 바뀌면 `Village`에 `setCovered(boolean)`를 열어 `cinematic.ts`가 직접 부르게 하는 쪽이 낫다.
- 영상 파일 이름은 `prelude-v3.mp4`처럼 버전이 들어 있다. 이제 1년 `immutable`이라 영상을 다시 만들면 새 이름을 써야 한다.
- `client/public/assets/abraxas/dream-test/`의 GLB 7개는 코드가 쓰지 않는데 `dist`에 들어간다.
