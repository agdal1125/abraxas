# 저폴리 아트 게이트

수치 검사를 통과해도 머리가 상자처럼 보일 수 있다. 합격 기준은 '이 크기에서 무엇으로 읽히는가'다.

## 1. 같은 조건으로 캡처

- `node scripts/dev-play.mjs <vite포트> <api포트>`로 게임을 띄우고 앱 창을 앞에 둔다. `tabs_context`가 패널이 숨겨져 있다고 하면 캡처하지 않는다. 숨김 상태에서는 장면이 멈추고 캡처가 잘린다. 뒤에 있는 탭은 초당 0.3프레임까지 떨어지므로 먼저 프레임 수를 잰다.
- 740×360과 844×390에서 캡처하고 DPR을 적는다.
- 전후는 같은 커밋 기준, 저장 상태, 카메라, 챕터로 비교한다. 다른 종횡비를 픽셀 개선 근거로 쓰지 않는다.
- 쓸 장면은 이동 화면, 대화 화면, 선택지 화면이다. Blender 프리뷰는 형태 확인용이고 합격 근거가 아니다.

## 2. 읽기 시험

이름표와 UI를 가리고 답한다.

| 질문 | 불합격 |
| --- | --- |
| 이 건물은 무엇을 하는 곳인가 | 이름표 없이 구별 못 함 |
| 저 인물은 누구인가 | 실루엣과 대표색으로 구별 못 함 |
| 다음에 어디로 갈 수 있는가 | 길과 막힌 곳이 안 읽힘 |
| 주인공은 어디 있는가 | 흰 덩어리로 뭉쳐 자리표시자처럼 보임 |

## 3. 형태와 표현

- 환경은 면이 보이는 플랫 셰이딩, 재료 색, 부재 단위 형태, 또렷한 빛이다(T018-P3). 인물 표현을 환경에 맞출지는 아직 사람 결정 사항이다.
- 재료 경계, 접지 그림자, 도구와 손의 연결을 본다. AO가 두 번 적용돼 검은 테두리가 생기지 않았는지 본다.
- 같은 소품, 같은 크기, 같은 방향이 한 화면에 3개를 넘지 않는다. 개수 대신 구역의 쓰임으로 판단한다. 여백은 이유를 말할 수 있으면 남긴다.
- 사람이 보는 차이가 표현 방식이면 배치를 고치기 전에 런타임에서 조명과 셰이딩을 바꿔 시험한다.

## 4. 측정 오염

선택 전후로 빛, 색, 소리, 시선, 식생이 달라져 정답처럼 보이는지 본다. 두 선택지의 경로 중 한쪽만 더 예쁘면 불합격이다.

## 5. 예산과 일치

```bash
node client/scripts/check-abraxas-assets.mjs
node scripts/check-village-reach.mjs
npm --prefix client run build
npm --prefix client run check:size
```

- 소스, metadata, GLB, manifest, 프리뷰가 같은 리비전인지 확인한다. 일부만 갱신했으면 적는다.
- 자산별 상한은 `asset-metadata.json`과 `docs/art/immersion-policy.md` 6절을 따른다.
- 고유 자산 합계와 화면의 드로콜은 다른 값이다. 드로콜과 프레임은 `threejs-mobile-perf`로 잰다.

## 6. 판정

`통과`, `수정 필요`, `사람 판단 필요` 중 하나를 쓰고 장면별 캡처 경로와 이유를 붙인다. 최종 인상은 사람이 고른다. 사람이 보기 전에는 다른 구역으로 넓히지 않는다.
